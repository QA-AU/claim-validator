# Generated claims — derived test cases, not restatements

Generated by `claude-haiku-4-5` from
[`source-simple-auth-api.txt`](source-simple-auth-api.txt) (the same
unmodified SimpleAuthAPI spec used in
[`../postman-auth-api-defects/`](../postman-auth-api-defects/)), with
this prompt:

> You are a QA engineer's copilot. Read the API specification below
> and write 15 integration TEST CASES for it — not restatements of
> the spec, but concrete test scenarios with a derived expected
> outcome, the kind you'd put in a test plan before writing the
> actual test code. Favor boundary conditions, sequences of calls,
> and computed expectations (e.g. what happens right at a limit,
> right after a timeout, or across a sequence of two calls) over
> simple single-fact checks.
>
> For each test case, write ONE sentence stating the expected outcome
> as a factual claim (not "test that X" — state directly what
> happens), the way a test assertion reads. Output ONLY a numbered
> list of 15 such claims, no preamble, no test names, no code.

This is the technique that actually produced an organic mistake, after
three earlier attempts (direct restatement on a small API doc, on a
40-claim detailed breakdown, and on a real financial report) all came
back essentially clean. The difference: asking for **derived** claims
— boundary conditions and cross-call synthesis — instead of direct
restatement, which forces the model to reason beyond what's literally
written rather than transcribe it.

1. When a user authenticates with valid credentials, the response includes a token with `token_type` equal to "Bearer" and `expires_in` equal to 3600 seconds.
2. When a user authenticates with an invalid password, the API returns 401 Unauthorized regardless of whether the username exists.
3. When the /authenticate endpoint receives a request missing the password field, the API returns 400 Bad Request.
4. When 100 requests are made from the same IP address within 60 seconds, the 101st request returns 429 Too Many Requests with X-RateLimit-Remaining equal to 0.
5. When a request is made exactly at the rate limit boundary (100th request in the window), the response includes X-RateLimit-Remaining equal to 0 but the request succeeds with the expected status code.
6. When the X-RateLimit-Reset timestamp passes, a new request from the same IP address succeeds and X-RateLimit-Remaining resets to 99 (assuming one request made).
7. When a valid token is used to call /user/profile, the response contains the authenticated user's username and email matching the account that generated the token.
8. When a token is used more than 3600 seconds after it was issued without being refreshed, calling /user/profile returns 401 Unauthorized.
9. When a refresh token is submitted to /refresh before the original token expires, a new token is returned with a fresh 3600-second expiration window.
10. When a refresh token is submitted to /refresh after it has expired, the API returns 401 Unauthorized.
11. When a user calls /logout with a valid token, subsequent requests using that same token return 401 Unauthorized.
12. When a request is made without an Authorization header to /user/profile, the API returns 401 Unauthorized.
13. When a request is made with a malformed Bearer token (invalid JWT structure) to /user/profile, the API returns 401 Unauthorized.
14. When a user authenticates, then immediately calls /user/profile with the returned token within the same minute, the X-RateLimit-Remaining header in both responses reflects consumption from the same 100-request-per-minute bucket.
15. When a request is submitted without the X-Request-ID header to any endpoint, the API either returns 400 Bad Request or accepts it and generates a tracking ID internally (depending on whether X-Request-ID is strictly required vs. optional).
