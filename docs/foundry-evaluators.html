Every evaluator in Microsoft Foundry, in one table

Microsoft Foundry (formerly Azure AI Foundry) ships roughly three dozen built-in evaluators spanning general response quality, translation-style textual similarity, RAG groundedness/relevance, content-safety risk detection, and AI-agent behavior — assembled per-project from a shared SDK rather than being one tool. This catalogs all of them, then compares the closest ones to what Claim Validator does.

Sourced from Microsoft's own reference docs, fetched live — Built-in Evaluators Reference and RAG Evaluators (Microsoft Learn, last updated late August 2026). Entries marked PREVIEW are in public preview per Microsoft's own docs — not GA, no SLA.

RAG evaluators

Assess retrieval quality and whether a response is actually backed by retrieved context — the category closest to what Claim Validator does, and the one detailed most below.

EvaluatorPurposeRequired inputsOutput
GroundednessDoes the response stay inside the retrieved context, without fabricating content? (precision)response, context (recommended), query optional1–5, pass/fail @ 3
Groundedness Pro PREVIEWSame question, decided by Azure AI Content Safety's own model instead of a bring-your-own judge.query, response, contextboolean pass/fail
RelevanceDoes the response accurately and completely address the query?query, response1–5, pass/fail @ 3
Response Completeness PREVIEWDoes the response cover everything the ground truth says it should? (recall)ground_truth, response1–5, pass/fail @ 3
RetrievalAre the retrieved context chunks actually relevant to the query? (no ground truth needed)query, context1–5, pass/fail @ 3
Document RetrievalComposite search-quality metrics (Fidelity, NDCG, XDCG, Max Relevance, Holes) against labeled ground truth.retrieval_ground_truth, retrieved_documentscomposite, 0–1 each
Groundedness and Response Completeness are explicitly framed by Microsoft as a precision/recall pair: Groundedness penalizes a response for saying too much (fabrication), Response Completeness penalizes it for saying too little (missing ground truth). Neither one alone answers both questions — you run both.

Compared to Claim Validator

Not a head-to-head between two competitors — Foundry is an evaluator toolkit you assemble per project; Claim Validator is one opinionated, deployed pipeline for one specific job. Here's where they actually overlap, and where they don't.

The closest analogue: Groundedness + Relevance

Feed Foundry's groundedness evaluator a response and context, and it asks almost the same question Claim Validator's entailment judge does: is this text actually backed by that source? The difference is in what the answer looks like.

Foundry Groundedness → 1–5 score, pass/fail @ 3
entails contradicts mentions_only no_evidence Claim Validator → 4-way verdict, 3-run majority vote

Microsoft Foundry

~35 orthogonal evaluators across quality, translation similarity, RAG, content safety, and agent behavior. You assemble the subset you need per project via the SDK or portal, each with its own data-mapping config and judge-model deployment.

Claim Validator

One pipeline, one job: given a document and a batch of bare claims, judge each as true, false, or unaddressed — plus a document-wide coverage gap report. Deployed as a standing, multi-tenant API, not an SDK you call from a notebook.

Microsoft FoundryClaim Validator
Verdict granularity A 1–5 score collapsed to pass/fail. A low Groundedness score doesn't say whether the response contradicted the source or just didn't address it — those read the same. Four distinct verdicts. contradicts and no_evidence are different outcomes on purpose — a fabricated claim and an unaddressed one need different follow-up.
Where the context comes from You supply it. Foundry's RAG evaluators score a context field in a dataset you already built — they don't run retrieval themselves (except Retrieval, which scores chunks you already retrieved). Built in. Resolves its own ontology + RAG index from the source document, cached by content hash and reused across submissions — nothing to pre-assemble.
Document-wide coverage No evaluator in the catalog asks this. Every RAG evaluator scores one response at a time against one context. A dedicated gap report: an exhaustive concept census used as ground truth for what no claim's citation ever touches.
Breadth Far broader — safety/content-moderation (hate, violence, self-harm, jailbreak, code vulnerability) and a full agent -evaluation suite (tool calls, task completion), none of which Claim Validator attempts. Deliberately narrow — validate-only, one document type of task. No safety scoring, no agent/tool evaluation.
Judge model Most evaluators take a deployment_name — an Azure OpenAI (or Foundry model catalog) deployment as judge. Anthropic-only by design, no OpenAI dependency anywhere in the pipeline.
Deployment shape An SDK + portal workflow — evaluation runs you kick off against a dataset, typically in CI or a notebook. A standing, multi-tenant HTTP API — async job submission, polling, Excel + JSON reports, per-tenant isolation.
Reach for Foundry when you're already inside the Azure AI ecosystem and want a governed, broad evaluation suite spanning quality, safety, and agent behavior across many projects. Reach for Claim Validator when the job is narrower and more concrete: you have a finished batch of claims about one document, from an LLM or anyone else, and need an independent, auditable true/false/unaddressed verdict on each — outside the Azure AI Foundry ecosystem entirely.
