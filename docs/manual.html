True, false, or never even claimed.

Your LLM just made a batch of claims about a document. Claim Validator catches which ones are actually true, which ones it made up, and which ones it dodged entirely — not by trusting the claim, and not by re-generating the document, but by retrieving the exact passages and judging entailment against them. Run at batch scale, so you're not interrogating a chatbot by hand to find out if today is the day it lied to you.

async job API Excel + JSON reports shared, reusable ontologies per-tenant isolation

Authentication

Every request under /api/ needs a bearer token, except the health check.

Authorization: Bearer <your-token>

Your token was issued when your tenant was set up — it's a fixed shared secret, not something you generate yourself. If a tenant is configured for Entra ID (Azure AD) instead, send a valid Entra ID access token in the same header; ask whoever set up your deployment which mode you're on.

A wrong or missing token always returns 401 — including on routes that would otherwise 404, so a failed request never confirms or denies whether something exists before you're authenticated.

Quick start

The whole workflow, start to finish. POST /api/validations returns in well under a second regardless of how long the actual judging takes — everything expensive happens after that response, in the background.

1

Upload your reference document

Get back a document_id to reference in the next step.

curl -H "Authorization: Bearer $TOKEN" \
  -F "file=@policy.txt" \
  https://<your-tenant>.azurecontainerapps.io/api/documents
{"document_id": "doc_e172825ccd7d", "filename": "policy.txt", "size_bytes": 626}
2

Submit your claims

Each claim needs just an id and its text — no schema, no metadata. You get a job_id back immediately.

curl -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "document": {"document_id": "policy", "files": ["/data/source/doc_e172825ccd7d/policy.txt"]},
    "claims": [
      {"id": "C1", "text": "A password reset link is valid for 15 minutes."},
      {"id": "C2", "text": "A user can request up to 5 reset emails per hour."}
    ]
  }' \
  .../api/validations
{"job_id": "job_c5aecef628c1", "status": "queued"}
3

Poll until it's done

Poll on whatever interval suits you — a typical claim set finishes in 30–90 seconds. status moves queued → running → done (or failed).

curl -H "Authorization: Bearer $TOKEN" \
  .../api/validations/job_c5aecef628c1
4

Read the verdicts, or download the report

The same GET above already returns every verdict as JSON once the job is done. For a document you can hand to someone else, download the Excel report from the URL it points you to.

curl -H "Authorization: Bearer $TOKEN" \
  -o report.xlsx \
  .../api/validations/job_c5aecef628c1/report

Endpoints

Everything under /api/, grouped by what it operates on.

Interactive reference: /docs — every deployment serves a live, auto-generated Swagger UI at https://<your-tenant>.azurecontainerapps.io/docs, always in sync with whatever's actually deployed. It sits outside /api/, so it's reachable without a token — a quick way to try a request or double-check a shape without leaving the browser.

Documents

EndpointWhat it does
POST/api/documents Upload a reference document (multipart). Returns a document_id to pass as document.files in a validation request. Capped at 25 MB by default.

Validations

EndpointWhat it does
POST/api/validations Submit claims for judging against a document — or against an existing ontology directly via ontology_key (see Reusing ontologies). Returns 202 immediately with a job_id.
GET/api/validations/{job_id} Status while running; the full result — every verdict, the gap report, quality metrics — once done. Only visible to whoever submitted it.
GET/api/validations/{job_id}/report Streams the .xlsx report. 409 if the job isn't done yet.
GET/api/validations/{job_id}/events Step-by-step phase trail (ontology resolution, retrieval, judging, completeness) — useful for seeing where time or tokens went.

Ontologies

EndpointWhat it does
GET/api/ontologies List every ontology that exists — shared across everyone on your tenant, browsable to pick one for reuse.
POST/api/ontologies Build one explicitly, ahead of submitting any claims — useful for pre-warming before a batch of validations that will all reuse it.
GET/api/ontologies/{key} Detail view — concept types discovered, whether it's fully indexed.
GET/api/ontologies/{key}/status Build progress for one in flight.
Ontologies are immutable and shared once built — permanent, listed, reusable by anyone on the tenant, never edited or deleted through the API. If a document set needs more content added, that's a new ontology, not a patch to an existing one.

Understanding verdicts

Every claim gets judged three times; the majority verdict is what's reported, alongside the agreement count so you can see when the judge wasn't unanimous with itself.

VerdictMeansWhat to do with it
entails The cited passage actually supports the claim. Nothing — this is the claim working as intended.
contradicts The cited passage says something that conflicts with the claim. The most actionable finding this tool produces — read it first.
mentions_only An on-topic passage exists, but it's silent on the specific thing the claim asserts. Not automatically wrong — often means the claim is more specific than the document. Worth a human look.
no_evidence Nothing in the document supports or contradicts it — retrieval found no relevant passage at all. A plausible-sounding claim the document never actually makes. Exactly what this tool exists to catch.

Each verdict also carries agreement (e.g. "3/3") and a one-line reason quoting or paraphrasing the passage the judge based its decision on — never take a verdict without reading the reason next to it.

The gap report

A separate statement from the per-claim verdicts — about the document, not the claims. Even a claim set that's 100% correct can still leave most of a document untouched.

For every concept type the document's own ontology discovered — grant types, error codes, whatever categories the document actually contains — the gap report says how many probable instances exist and how many your claims ever cited. A concept with addressed_count: 0 means none of your claims reference it at all, named explicitly in claims_never_addressed.

Three perfectly-entailed claims can still leave a gap report showing your claim set only actually reaches a fraction of what the document says. Read both reports — one tells you if your claims are correct, the other tells you if they're complete.

Reusing ontologies

Building an ontology — reading the document, discovering its concepts, indexing it for retrieval — is the expensive part of a validation. Two ways to skip paying for it twice.

Automatic, by content

Submit the identical document bytes again — under any document_id, or none — and it's detected by content hash and reused automatically. No action needed on your part; this happens by default on every submission.

Explicit, by picking from the list

Already know which ontology you want? Skip the document upload entirely and reference it directly:

curl -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "document": {"files": []},
    "ontology_key": "policy-1a2b",
    "claims": [{"id": "C1", "text": "..."}]
  }' \
  .../api/validations

Browse GET /api/ontologies first to find the key you want — every entry lists who built it, when, and how many concept types it discovered, so you can tell one apart from another before committing to it.

The Excel report

Written alongside the JSON result from the same in-memory data, so the two formats never drift apart from each other. Three sheets:

Claims

Every claim, its verdict, agreement, cited passages, and the judge's reason — side by side, reviewable in one pass.

Gaps

The gap report in tabular form — concept, probable instance count, which ones your claims addressed, which they never touched.

Quality

Aggregate metrics — entailed, contradicted, no_evidence counts, token spend by phase, judge agreement — each with what it measures and how to read it, not just a bare number.

Errors

CodeMeans
400Malformed request — most commonly, a validation submitted with neither document.files nor ontology_key. Provide one or the other.
401Missing or invalid token. Also returned — deliberately, not 403 — for a job that exists but belongs to someone else, so a guessed job_id never confirms it exists.
404No such job, document, or ontology key — or one that exists but isn't yours.
409The report isn't ready yet — the job hasn't reached done.

Tenancy & isolation

Each tenant is a fully independent deployment: its own token, its own database, its own Anthropic key, its own storage. Nothing about how the API behaves changes between tenants — only the URL and the token do.

Within one tenant, job and report privacy is scoped to the identity your request authenticates as — but what that identity is depends on how your tenant is configured. With Entra ID (Azure AD) auth configured, that's genuinely per-signed-in-person: your jobs are invisible to a colleague on the same tenant with their own token. With the default shared-secret token, everyone holding that one token is treated as a single identity — jobs submitted by anyone with the token are visible to anyone else with it. Ask whoever set up your deployment which mode you're on before assuming the stronger guarantee. Ontologies are shared either way: built once, listed for everyone on the tenant, reused by anyone who picks them.
