Two Tenants, One Codebase, No Shared Data

How the silo deployment holds together on Azure, and what actually happens between a client's upload and its downloaded report.

Architecture — infrastructure

Every user gets an identical, independently deployed stack — its own Container App, Key Vault, and file share. Only two things are genuinely shared: the Container Apps environment they run inside, and a single Postgres server that hosts a separate database per tenant. The boundary that actually matters is the database, not the server.

Request Flow — one validation job

The submit call returns in well under a second — everything expensive happens after that response has already gone back to the caller. This is the actual mechanism jobs.py exists to guarantee: not "eventually async," but genuinely decoupled from the first response.

Reading Notes

Why a database, not a server, per tenant

A separate Postgres server per user would double the isolation guarantee at real ongoing cost. A separate database on one shared server keeps data fully partitioned — different name, different connection string — without paying for N servers.

Why the 202 line matters

Nothing about the response depends on the entailment judge, the census, or the report actually finishing. A slow document doesn't make the API call slow — only the polling does.

What crosses a silo boundary

Exactly two things: a database connection into that tenant's own database, and an outbound call to Anthropic using that tenant's own key. Nothing else — no shared cache, no shared queue, no shared file path.
